# Phase 7: GDPR Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development
> (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use
> checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make the two rights that need code — access and erasure — actually work across every
table that holds personal data, put an expiry on the data that has none, and generate the Article 30
record from the same source so it cannot drift from what the system does.

**Architecture:** One registry in code naming every table that links to a person, how it links, and
what erasure does to it. Export, erasure, retention and the processing record all read that
registry, so adding a table to the system without adding it to the registry fails a test rather
than quietly creating an unerasable corner.

**Tech Stack:** PostgreSQL, SQLAlchemy async, Alembic, FastAPI, Celery.

**Spec:** `docs/superpowers/plans/2026-08-01-production-readiness-roadmap.md` — the GDPR row in §2
and the Phase 7 line in §3, plus `docs/personal-data-inventory.md` started in Phase 5.

## Global Constraints

- **The registry is the single source of truth.** Export, erasure, retention and the Article 30
  record are all derived from it. Two lists of personal data disagree within a release.
- **Erasure is deletion unless there is a documented reason it cannot be.** Anonymised retention is
  a lawful-basis argument, not an engineering convenience, and every exception is named in the
  processing record with the ground it relies on.
- **The audit log is not erased.** It carries database triggers refusing UPDATE and DELETE, and it
  is the evidence that access controls worked. Retained under Article 17(3), which is a legal
  position the owner must confirm — see "The conflict this phase cannot engineer away".
- **Export includes everything, including what erasure will not remove.** The right of access and
  the right to erasure are different rights; refusing to show someone the audit entries about them
  because they cannot be deleted confuses the two.
- **A subject request is itself an audited event.** Who asked, when, and what was returned.
- **Every dialect-specific query is tested against real PostgreSQL** with `REQUIRE_POSTGRES=1`.
- Backend gate per task: `pytest tests/ -q --no-cov`, `pytest -m postgres`, `black --check .`,
  `ruff check .`, `mypy api worker shared`, `scripts/evaluate_search.py`. Frontend tasks add tests,
  typecheck, lint, build, `verify:routes`. Both audit jobs run before every push.

## The conflict this phase cannot engineer away

Erasure and an append-only audit trail pull in opposite directions, and no amount of code resolves
it. `audit_log` holds `actor_email`, `client_ip` and `user_agent` — personal data by any reading —
behind triggers that make the database refuse to modify or delete a row. That immutability is the
point: it is what makes the log evidence rather than a diary.

Three options exist and only one is honest:

1. **Delete the audit rows.** Requires dropping the triggers, which destroys the guarantee for
   every other row and every future audit.
2. **Pseudonymise at write time.** Correct for a system not yet built; it does nothing for rows
   already written and weakens the trail that is the log's reason to exist.
3. **Retain, and say so.** Article 17(3)(b) and (e) permit retention for legal obligations and for
   the establishment or defence of legal claims. Access controls on procurement data are exactly
   that.

This plan takes option 3, records it as a limitation rather than a feature, and marks it for the
owner's legal sign-off. Task 5 writes it into the processing record where a regulator would look
for it. What engineering can do — and Task 1 does — is stop the list of such exceptions growing
without anybody noticing.

## File Structure

- `shared/procuresignal/privacy/inventory.py`: the registry — every table, its link to a person,
  its erasure action, its retention window, its lawful basis.
- `shared/procuresignal/privacy/subject.py`: export and erasure, both driven by the registry.
- `shared/procuresignal/jobs/retention.py` (modify): windows for the tables that have none.
- `api/routers/privacy.py`, `api/schemas/privacy.py`: the subject-request endpoints.
- `docs/personal-data-inventory.md` (rewrite): generated from the registry.
- `docs/processing-record.md`: the Article 30 record, generated, with the wording marked for legal.
- `scripts/generate_privacy_docs.py`: writes both documents from the registry.

### Task 1: The registry, and a test that keeps it honest

**Files:**
- Create: `shared/procuresignal/privacy/__init__.py`, `shared/procuresignal/privacy/inventory.py`
- Test: `tests/unit/test_privacy_inventory.py`

**Interfaces:**
- Produces: `SubjectLink` enum (`USER_ID_INT`, `USER_PUBLIC_ID`, `ORGANIZATION`, `NONE`);
  `ErasureAction` enum (`DELETE`, `ANONYMISE`, `RETAIN`);
  `PersonalDataTable(table, model, link, link_column, erasure, retention_days, purpose,
  lawful_basis, retention_note)`; `INVENTORY: tuple[PersonalDataTable, ...]`;
  `def tables_for(link: SubjectLink) -> tuple[PersonalDataTable, ...]`;
  `def unregistered_tables() -> set[str]`.

**Design notes:**

The registry is a list of facts about tables, not code that touches them. Tasks 2–5 all read it,
which is what stops export, erasure, retention and the Article 30 record from disagreeing — the
usual way a privacy programme fails is four documents maintained separately.

`SubjectLink` exists because this codebase links to people two ways and the difference is not
cosmetic. Phase 1–2 tables (`chat_conversations`, `user_news_preferences`) store `User.public_id` in
a `String` column; Phase 4–6 tables (`notifications`, `search_feedback`, `agent_runs`) use an integer
foreign key. An erasure that assumes one shape silently misses every table of the other, and the
miss looks exactly like success.

`unregistered_tables()` compares `Base.metadata` against the registry and returns what is not
accounted for. The test asserts it is empty, so adding a table to the system without deciding
whether it holds personal data fails the build. Tables genuinely holding none are registered with
`SubjectLink.NONE` — an explicit decision with a name on it rather than an omission.

- [x] Step 1: Failing test — every table in `Base.metadata` is registered; every registered table
      exists; a `DELETE` action is never paired with `SubjectLink.NONE`
- [x] Step 2: Enumerate the schema and write the registry, one decision per table
- [x] Step 3: Failing test — `audit_log` is registered `RETAIN` and names its Article 17(3) ground
- [x] Step 4: Full gate, commit, push

### Task 2: An expiry on the data that has none

**Files:**
- Modify: `shared/procuresignal/jobs/retention.py`, `worker/tasks.py`
- Test: `tests/unit/test_retention.py` (extend), `tests/postgres/test_retention_pg.py`

**Interfaces:**
- Consumes: `INVENTORY` (Task 1).
- Produces: `prune_expired_records` covering every table whose registry entry has a
  `retention_days`; `RetentionResult` gains a `by_table: dict[str, int]`.

**Design notes:**

`search_feedback` has no expiry today, deliberately: Phase 5 wanted a training set that outlives the
30-day article window, and said so. That was a defensible engineering trade and it is not a
defensible privacy position — it makes the one table in the system where personal data never
expires. This task gives it 400 days, which is long enough for a train/test split across a full
procurement cycle and short enough to be a limit.

`agent_runs` inherits the same treatment at 400 days: a transcript is a record of what a named
person asked about a supplier.

Driving the deletes from the registry rather than from a hand-written list is what stops the job
and the inventory drifting. A table with a `retention_days` that the job does not prune is a lie in
a compliance document, so a test asserts the two agree.

- [x] Step 1: Failing tests — every registry entry with a window is pruned by the job; entries
      without one are untouched; `by_table` reports what went
- [x] Step 2: Implement, driving the deletes from the registry
- [x] Step 3: Failing Postgres test — pruning a user's rows leaves other users' rows alone
- [x] Step 4: Full gate, commit, push

### Task 3: Subject access export

**Files:**
- Create: `shared/procuresignal/privacy/subject.py`
- Create: `api/routers/privacy.py`, `api/schemas/privacy.py`
- Modify: `api/main.py`
- Test: `tests/unit/test_subject_export.py`, `tests/integration/test_privacy_api.py`

**Interfaces:**
- Consumes: `INVENTORY`, `SubjectLink` (Task 1).
- Produces: `async def export_subject(session, *, user) -> SubjectExport` with
  `SubjectExport(subject: dict, generated_at: datetime, tables: dict[str, list[dict]])`;
  `GET /api/privacy/me/export` (any authenticated user, their own data);
  `GET /api/privacy/users/{public_id}/export` (admin, same organization).

**Design notes:**

Export walks the registry rather than a hand-written set of queries, so a table added in Phase 8
appears in the export the moment it is registered.

It includes tables erasure will not touch, `audit_log` first among them. Access and erasure are
different rights, and hiding the audit entries about someone because they cannot be deleted answers
a question nobody asked.

An admin may export a member of their own organization, because a subject request usually arrives
by email to the company rather than through the product. Cross-organization is a 404.

The export is JSON. A human-readable format is a nicety; a machine-readable one is what Article 20
asks for, and it is what a lawyer forwards.

      never do; both link shapes resolve; the export is JSON-serialisable
- [x] Step 2: Implement `export_subject`
- [x] Step 3: Failing tests — self-export needs no role, admin export is organization-scoped,
      cross-organization is a 404, and the request is audited
- [x] Step 4: Implement the endpoints, register in `api/main.py`
- [x] Step 5: Full gate, commit, push

### Task 4: Erasure

**Files:**
- Modify: `shared/procuresignal/privacy/subject.py`, `api/routers/privacy.py`
- Test: `tests/unit/test_subject_erasure.py`, `tests/postgres/test_subject_erasure_pg.py`

**Interfaces:**
- Consumes: `INVENTORY`, `ErasureAction` (Task 1).
- Produces: `async def erase_subject(session, *, user, reason) -> ErasureReceipt` with
  `ErasureReceipt(subject_public_id, erased_at, deleted: dict[str, int], anonymised: dict[str, int],
  retained: dict[str, int])`; `POST /api/privacy/users/{public_id}/erase` (admin, same
  organization).

**Design notes:**

The receipt is the deliverable, not the deletion. A controller has to be able to answer "what did
you do with my data" with something more than an assurance, and `retained` is the field that makes
the receipt honest — it names the audit rows that survive and why.

Erasure is not the same as deleting the user row and relying on cascades. Cascades cover the tables
that have foreign keys; the `public_id`-linked tables from Phases 1–2 have none, and would be left
behind with a dangling identifier. That is the failure this task exists to prevent, and a Postgres
test asserts every registered table is empty of the subject afterwards.

The user row itself is deleted last, so a failure part-way leaves the account intact and the
operation repeatable rather than half-done with no way to find the remainder.

Erasing is audited before the user disappears — the audit row names the actor, the subject's public
id, and the counts. The subject's own row cannot be the actor.

- [x] Step 1: Failing tests — every registered table is empty of the subject afterwards, including
      the `public_id`-linked ones; another user's rows are untouched; the receipt counts match
- [x] Step 2: Implement `erase_subject`
- [x] Step 3: Failing test — `audit_log` rows survive and are reported as retained, not deleted
- [x] Step 4: Failing Postgres test — erasure against the migrated schema, with the append-only
      triggers live, does not raise
- [x] Step 5: Endpoint, admin-only, organization-scoped, audited
- [x] Step 6: Full gate, commit, push

### Task 5: The processing record, generated

**Files:**
- Create: `scripts/generate_privacy_docs.py`, `docs/processing-record.md`
- Modify: `docs/personal-data-inventory.md` (regenerated), `.github/workflows/ci.yml`
- Test: `tests/unit/test_privacy_docs.py`

**Interfaces:**
- Consumes: `INVENTORY` (Task 1).
- Produces: `generate_privacy_docs.py --check` exiting non-zero when either document is stale.

**Design notes:**

Both documents are generated from the registry and CI fails when they are out of date, the same
shape as the search floor gate. A hand-maintained Article 30 record is accurate on the day it is
written and wrong within two releases, and the wrongness is invisible until a regulator reads it.

What the generator cannot produce is the wording that requires a lawyer: the controller's identity,
the lawful basis for each purpose, retention justifications, and the international-transfer
position. Those are marked `OWNER INPUT REQUIRED` in the output rather than filled with something
plausible. A processing record containing a guess about lawful basis is worse than one with a gap,
because the gap is visible.

## Self-Review

**Spec coverage:** The roadmap's Phase 7 line is "retention enforcement, DSAR export, erasure,
processing records" — Tasks 2, 3, 4 and 5. Task 1 is the registry the other four read, and it is
what makes the roadmap's "GDPR is legal and operational work, not only code" tractable: the code
part is enumerable and enforced, and what remains is marked for the owner rather than guessed. The
5–6 task estimate matches.

**Ordering:** 2, 3, 4 and 5 all consume Task 1's registry. 4 extends 3's module. 5 documents what
1 declares.

**Type consistency:** `SubjectLink` and `ErasureAction` (Task 1) are what `export_subject` (Task 3)
and `erase_subject` (Task 4) switch on. `PersonalDataTable.retention_days` is what Task 2's job
prunes by and Task 5's document reports.

**Deliberately out of scope:**

- **Consent management.** There is no consent-based processing in this system; the lawful basis for
  a procurement tool used by an employer's staff is contract or legitimate interests. Building a
  consent store would imply a basis that does not apply.
- **Data residency.** The roadmap defers it to hosting, which the owner has not chosen. It stays a
  constraint on that decision rather than code.
- **Erasing the audit log.** See "The conflict this phase cannot engineer away".
- **A self-service erasure button.** Erasure is irreversible and the requester is usually not the
  subject. An admin-only endpoint with an audited receipt is the right shape until there is a
  verified-identity flow to hang self-service off.
